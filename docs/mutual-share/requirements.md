# 互相分享（Mutual Share）需求说明

日期：2026-07-20  
状态：已确认（决策见 §10）  
关联设计：[architecture.md](./architecture.md)

## 1. 背景

当前 Instant Share 为**单向分享**：

- 本机 Flutter 作为唯一 `admin`，控制本机 Go 服务启停与文件/文章列表。
- 对方通过 HTTP `/share` 只读浏览与下载。
- 文件始终留在分享者本机，下载地址指向分享者服务。

产品希望支持：**双方都安装 Instant Share 并开启服务后，经主机同意组成临时共享房间**，在房间内看到彼此发布的文件，并直连文件所有者下载。大文件不得上传到对方磁盘。

## 2. 目标

1. 主机 A 开启分享后，对端 B 可通过输入 A 的 IP（可带端口）发起连接申请。
2. A 在「连接」Tab 审批（同意 / 拒绝）；B 端等待认证，超时 60 秒。
3. 同意后 B 以 `peer` 身份加入 A 主持的共享会话（**不是**第二个 `admin`）。
4. B 加入成功后 UI 进入「已加入共享」态（分享色背景、顶栏由 `[分享文章 | 分享文件]` 切换为 `[共享文件]`）。Host 顶栏**不变**。
5. 房间内各方发布的文件**字节留在所有者本机**；App 内共享目录只同步元数据；下载 URL 指向所有者的 `base_url`。
6. A（host）负责配对、聚合共享列表、经 WS 向已批准 Peer 推送变更通知。
7. 允许多个 Peer 同时加入同一 Host 房间。
8. PC Web（`/share`）在房间有效时展示**房间聚合目录**（Host 与 Peer 双方链接均可见所有成员已 offer 的文件）；下载直连文件所有者本机，不经第三方中转。

## 3. 非目标（本期不做）

| 项 | 说明 |
|----|------|
| 下载鉴权 / 短期 token | 明确不做；知道 URL 即可按现有公开下载逻辑访问 |
| B 以 `admin` 连接 A 的 WS | 禁止；避免双 admin 互踩与越权停服 |
| 文件上传/中转到主机磁盘 | 禁止作为默认路径；大文件一律本机链接 |
| 纯浏览器访客回传文件 | 本期要求对方也安装 App 并开服务 |
| 公网 / 跨 NAT 穿透 | 仅保证同一局域网可达 |
| 多于一个 host 的联邦房间 | 一个共享房间仅一个 host（A） |
| 文章互相编辑 / 实时协作 | 文章未做到多机不重复；Peer 入房后顶栏只留「共享文件」 |
| Host 代理 / 中转下载他机文件 | 明确不做；Web 下载他机文件直连所有者 |
| 多机文章聚合 | 文章仍只展示**当前打开这台机器**的本机文章 |
| 单 Peer 限制 | 明确支持多 Peer |

## 4. 角色与术语

| 术语 | 含义 |
|------|------|
| Host（主机） | 先开启分享、接受配对审批的一方（文中称 A）。本机仍是自己服务的唯一 `admin`。 |
| Peer（对端） | 经审批加入房间的一方（文中称 B）。对 Host 的 WS 使用角色 `peer`。 |
| 本机 admin | 仅控制**自己**本机 Go 服务（`share.start/stop/sync`），始终走本机地址。 |
| 共享房间 | 以 Host 的服务为协调中心的临时会话；成员含 Host + 已批准 Peer。 |
| 文件所有者 | 文件物理路径所在设备；下载必须打到该设备的 HTTP 服务。 |

角色相对**某台服务**成立，不是人的全局身份：

- A 对本机服务 = `admin`；对 B 服务若访问其文件 = 普通下载客户端。
- B 对本机服务 = `admin`；对 A 的房间 WS = `peer`。

## 5. 用户故事

### US-1 主机开启可被连接的分享

作为主机 A，我点击中央开关开启分享后，局域网内暴露 HTTP 与 WS，以便对端发起连接。

**验收**

- A 分享开启后可得到可达的 `http://<lan_ip>:<port>` 与 `ws://<lan_ip>:<port>/ws`。
- A 本机 admin 行为与现网一致（选文件、同步、停止分享）。

### US-2 对端发起连接并等待审批

作为对端 B，我点击首页**右上角「+」按钮**，弹出对话框输入 A 的 IP（可选端口），确认后进入「等待对方认证…」，倒计时 60 秒。

**验收**

- 入口为首页右上角 `+`，与底部摘要栏「添加文件」加号、中央主按钮加号语义分离。
- 非法 IP / 不可达时有明确错误提示，不进入无意义等待。
- 等待期间可取消；超时提示并可重试。
- A 侧「连接」Tab 出现待审批项（设备名 / IP / 申请时间）。

### US-3 主机审批连接

作为主机 A，我在「连接」Tab 同意或拒绝 B。

**验收**

- 同意后 B 在倒计时内收到成功，进入「已加入共享」UI。
- 拒绝后 B 立即结束等待并提示被拒绝。
- 超时未操作视为失败；A 侧待审批项清除或标记过期。

### US-4 对端加入后的 UI

作为对端 B，加入成功后：

1. 界面切换为分享主题色（与本地「分享中」视觉一致或可区分的「已加入共享」色）。
2. 顶栏 `[分享文章 | 分享文件]` 动画切换为 `[共享文件]`（因文章尚未支持多机器不重复共享；Peer 侧只呈现文件房间态）。

作为主机 A：

- 顶栏**保持** `[分享文章 | 分享文件]`，不切换为「共享文件」。
- 本机文章 / 文件分享流程与现网一致。

**验收**

- 仅 Peer 在 `joinedRoom` 时切换顶栏；Host 顶栏无此动画。
- 状态可逆：退出房间 / 主机解散 / 连接断开后 Peer 恢复本地未加入态。
- 动画与配色不阻塞功能可用性。

### US-5 对端发布本机文件到共享列表

作为对端 B，我选择本机文件发布到房间后，列表出现该文件，但文件仍在 B 磁盘；他人下载时请求 B 的服务。

**验收**

- 发布仅同步元数据（名称、大小、所有者、`base_url`、下载 path）。
- 不出现向 A 上传文件体的默认流程。
- A / 其他成员下载 B 的文件时，HTTP 目标主机为 B 的 IP/端口。

### US-6 主机发布本机文件

作为主机 A，我继续用现有方式管理本机分享文件；这些文件进入 App 房间目录（供 Peer 看见），下载地址指向 A。

**验收**

- 与现有 `ShareService` 路径分享模型兼容。
- 列表变更通过 WS 通知已连接 Peer。
- 浏览器打开 A 的 `/share` **能看到** B 已 offer 的文件，下载请求打到 B 的 IP。

### US-7 列表变更通知（App 房间目录）

作为房间内的 App 成员，当任一方增删共享文件时，我能在合理时间内看到更新的房间目录。

**验收**

- Host 通过 WS 向已批准 Peer 推送目录/变更通知。
- Peer 断线重连后能拉到当前聚合目录（或等价全量快照）。
- PC Web 通过 `GET /api/v1/share/status` 与 viewer `share.status` 推送获取聚合目录；catalog 变更时 Web 页近实时刷新。
- 离房或房间关闭后，Web 不再展示对方文件，回到本机 `ShareStatus`。

### US-8 大文件不压垮主机

作为主机 A，即使 Peer 分享 10GB 级文件，我的磁盘与内存也不会因「中转存储」而暴涨。

**验收**

- 默认路径无「Peer → Host 落盘」传输。
- 文档与实现均以所有者本机下载为准。

## 6. 功能需求明细

### 6.1 连接入口（B）

- 入口：首页**右上角「+」按钮**（`HomeSharePageShell.topRight` 区域；与底部「添加文件」、中央主操作加号分离）。
- 点击后弹出对话框：输入对方 IP，可选端口（默认沿用产品默认端口或设置中的端口约定）。
- 确认后发起配对请求，展示等待态 + 60s 倒计时。

### 6.2 配对与审批（A）

- 「连接」Tab 展示：待审批 / 已连接成员。
- 支持**多个 Peer** 同时 pending / 已连接。
- 操作：同意、拒绝。
- 超时：60 秒，双方状态一致收敛到失败。

### 6.3 房间目录（App + PC Web）

房间聚合目录在 Desktop App（Host / Peer）与 PC Web `/share` 共用。Web 列表来源：公开房间目录非空 → 用房间 catalog 映射为 `files`；否则 → 本机 `ShareStatus.files`。文章始终本机，不合并房间。

每条文件记录至少包含：

| 字段 | 说明 |
|------|------|
| id | 文件 ID（所有者侧生成） |
| name | 展示名 |
| size | 字节大小 |
| owner_id | 所有者设备标识 |
| owner_display_name | 可选展示名 |
| base_url | 所有者服务根地址，如 `http://192.168.1.20:8080` |
| download_path | 相对路径，如 `/api/v1/share/files/{id}/download` |

完整下载 URL = `base_url` + `download_path`。

### 6.4 本机服务前提

- Host 与 Peer **均需**启动本机 Instant Share 服务。
- Peer 发布文件前，文件须已挂入 Peer 本机 `ShareService`（或等价本机分享状态），以便其 HTTP 可下载。

### 6.5 会话结束

以下任一情况应退出「已加入共享」或清理成员关系（具体文案实现期定）：

- Peer 主动断开 / 退出房间
- Host 停止分享或关闭服务
- 网络不可达超过约定心跳/探测失败

Host 停止分享后，房间解散；Peer UI 恢复本地态。

## 7. 交互流程（摘要）

```text
1) A 点中央开关 → 本机服务 + share 会话启动
   暴露 http://192.x.x.x:port 与 ws://192.x.x.x:port/ws

2) B 点首页右上角「+」→ 弹窗输入 A 的 IP（可带端口）→ 确认
   B → A: pairing.request { device_id, display_name, request_id }
   B UI: 「等待对方认证…」倒计时 60s

3) A「连接」Tab 出现待审批（可同时有多个 Peer）
   同意 → pairing.approve
   拒绝 → pairing.reject
   超时 → pairing.timeout（或等价失败）

4) B 收到 approve
   → 以 role=peer 进入正式会话
   → B UI: 分享色 + 顶栏「共享文件」
   → A UI: 顶栏仍为 [分享文章 | 分享文件]

5) 发布与下载（App 房间目录）
   任一方在本机挂载文件后，向房间同步 share.offer（仅元数据）
   Host 聚合目录并向 Peers notify
   下载直连文件所有者 base_url，不经 Host 中转落盘
   PC Web /share 展示房间聚合目录；下载直连所有者
```

## 8. 边界与异常

| 场景 | 期望 |
|------|------|
| IP 不可达 | 连接前或请求失败时提示，不无限等待 |
| 扫到/连到自己 | 拒绝或提示「不能连接本机」 |
| Peer 发布后关闭服务 | 其文件在列表可保留但下载失败，并提示所有者离线（实现期可简化为下载失败提示） |
| 双方端口不同 | 以输入/协商的 port 为准，写入 `base_url` |
| 多网卡 | `base_url` 使用对端可达 IP（配对时使用的 IP 优先） |
| 重复申请 | 同一 device 重复 pending 时合并或拒绝新申请（实现期二选一，需在任务中写死） |

## 9. 成功标准

1. 两台及以上局域网设备可完成：开分享 → 申请 → 审批 → App 内看到房间目录 → 互下对方大文件且 Host 磁盘无明显额外占用。
2. Peer 无法调用 Host 的 `share.stop` 等 admin 控制指令。
3. Host 顶栏仍为文章/文件切换；仅 Peer 进入「共享文件」顶栏。
4. PC Web `/share`：A、B 双方分享链接均可见房间聚合文件；下载各打所有者；离房后对方文件从 Web 消失。

## 10. 已确认决策

| # | 议题 | 结论 |
|---|------|------|
| 1 | 连接入口 | 首页**右上角「+」** → 弹窗输入对方 IP（可带端口） |
| 2 | 成员数 | **允许多 Peer** 加入同一 Host 房间 |
| 3 | Host 顶栏 | **不变**，仍为 `[分享文章 \| 分享文件]`；仅 Peer 切 `[共享文件]`（文章尚未多机去重） |
| 4 | PC Web | **`/share` 展示房间聚合目录**；本机文件相对 URL、他机绝对 URL；批量下载仅同源文件 |
